TokenHSI_g1 G1 Import Chain Notes
=================================

Purpose
-------
This note records where the original TokenHSI stack was adapted so that
g1_dex3_ori.urdf is imported as the active robot, and how the G1 asset,
DoF/action dimensions, AMP motion data, and IsaacGym body order are connected.


Main G1 Replacement Points
--------------------------

1. Environment config selects the G1 asset.

   File:
     tokenhsi/data/cfg/multi_task/amp_g1_dex3_traj_sit_carry_climb.yaml

   Key field:
     assetFileName: "mjcf/g1_dex3_ori.urdf"

   This is the first entry point. IsaacGym loads this URDF instead of the
   original humanoid MJCF. The same config also uses G1 link names for
   keyBodies/contactBodies, for example wrist and ankle links.


2. Humanoid recognizes G1 Dex3 assets.

   File:
     tokenhsi/env/tasks/humanoid.py

   G1 asset set:
     G1_DEX3_ASSET_FILES = {
         "mjcf/g1_dex3.urdf",
         "mjcf/g1_dex3_ori.urdf",
     }

   This allows the shared Humanoid base class to select the G1-specific
   character properties branch.


3. G1 DoF/action/observation dimensions are registered.

   File:
     tokenhsi/env/tasks/humanoid.py

   Function:
     _setup_character_props()

   G1 branch:
     self._dof_offsets = list(range(44))
     self._dof_obs_size = 43 * 6
     self._num_actions = 43
     self._num_actions_joint = self._num_actions

   Meaning:
     - G1 Dex3 has 43 actuated 1-DoF joints.
     - Policy action dimension is 43.
     - AMP dof observation uses 43 joints * 6D representation.
     - _dof_offsets has length 44 because it stores cumulative offsets.

   If this branch were not active, the policy, PD targets, dof_pos/dof_vel,
   and AMP observations would still be interpreted as the original humanoid
   dimensions, which would make G1 training invalid.


4. IsaacGym actual body names are captured after asset loading.

   File:
     tokenhsi/env/tasks/humanoid.py

   In _create_envs(), after gym.load_asset():
     self._asset_body_names = list(self.gym.get_asset_rigid_body_names(humanoid_asset))
     self.num_dof = self.gym.get_asset_dof_count(humanoid_asset)

   This matters because IsaacGym may expose the URDF body order differently
   from a naive text traversal. Later body mapping uses the actual body order
   returned by IsaacGym.


5. Multi-task AMP observation size follows G1 dimensions.

   File:
     tokenhsi/env/tasks/multi_task/humanoid_traj_sit_carry_climb.py

   Function:
     _setup_character_props()

   G1 branch:
     self._num_amp_obs_per_step =
         13 + self._dof_obs_size + self._num_actions + 3 * num_key_bodies

   Since _dof_obs_size is 43 * 6 and _num_actions is 43, AMP observation
   layout is resized for G1.


6. MotionLib dispatches GMR robot motion yaml to GMRRobotMotionLib.

   File:
     tokenhsi/utils/motion_lib.py

   Function:
     MotionLib.__new__()

   Behavior:
     If the motion yaml has:
       format: gmr_robot_motion

     then MotionLib returns:
       GMRRobotMotionLib(...)

   This avoids sending GMR-retargeted G1 pkl files through the original
   poselib/SMPL-style MotionLib path.


7. GMRRobotMotionLib loads or reconstructs the fields needed by AMP.

   File:
     tokenhsi/utils/gmr_robot_motion_lib.py

   Required fields:
     fps
     root_pos
     root_rot
     dof_pos

   Preferred precomputed fields, if present:
     root_vel
     root_ang_vel
     dof_vel
     body_pos
     body_rot
     body_vel
     body_ang_vel

   Fallback computation:
     - root_vel and dof_vel by finite difference.
     - root_ang_vel from quaternion delta.
     - body_pos from local_body_pos and root pose if body_pos is absent.
     - body_rot from precomputed field if present, otherwise FK/fallback.
     - body_vel and body_ang_vel by finite difference/quaternion delta.

   This keeps get_motion_state() and get_motion_state_max() compatible with
   the environment and AMP builders.


8. Motion body schema is mapped to IsaacGym asset body schema.

   Files:
     tokenhsi/env/tasks/multi_task/humanoid_traj_sit_carry_climb.py
     tokenhsi/utils/body_schema.py

   Environment side:
     _load_motion_body_names()
     _build_motion_key_body_ids()
     _build_asset_to_motion_body_ids()
     _map_motion_body_state_to_asset()

   Mapping helper:
     build_asset_to_motion_body_mapping()
     map_motion_body_state_to_asset()

   Purpose:
     GMR motion body order and IsaacGym-loaded URDF body order may differ.
     The mapping is built by body name, not by raw array index. If an Isaac
     body is not present in the motion schema, it falls back to its parent
     body and applies a rest-pose position offset.


Representative Function: _setup_character_props()
--------------------------------------------------

File:
  tokenhsi/env/tasks/humanoid.py

This function is effectively the robot specification registry. It reads:

  asset_file = self.cfg["env"]["asset"]["assetFileName"]

Then it chooses the proper branch for the loaded robot. For G1 Dex3 it does:

  body_names, body_parent_names, body_rest_pos, dof_body_ids =
      self._parse_g1_asset_body_info(asset_file)
  self._asset_body_names = body_names
  self._asset_body_parent_names = body_parent_names
  self._asset_body_rest_pos = body_rest_pos
  self._dof_body_ids = dof_body_ids
  self._dof_offsets = list(range(44))
  self._dof_obs_size = 43 * 6
  self._num_actions = 43
  self._num_actions_joint = self._num_actions
  self._num_obs = 1 + len(body_names) * (3 + 6 + 3 + 3) - 3

Interpretation:

  - _parse_g1_asset_body_info() reads the URDF/MJCF body tree.
  - dof_body_ids records which body each actuated joint belongs to.
  - _dof_offsets = list(range(44)) means 43 scalar 1-DoF joints.
  - _dof_obs_size = 43 * 6 means each scalar joint is represented as a 6D
    observation block in AMP/self observation builders.
  - _num_actions = 43 means policy output and PD targets are G1-sized.
  - _num_obs is recomputed from the actual number of G1 bodies.

This function is one of the main reasons G1 is actually loaded as a G1 model
instead of being interpreted through the original humanoid dimensions.


Current Assessment
------------------

The code path is now G1-aware in these layers:

  - Asset selection.
  - IsaacGym asset loading.
  - DoF/action dimensions.
  - AMP observation dimensions.
  - GMR motion loading.
  - Motion body to Isaac body mapping.
  - G1 locomotion reward.

The remaining high-risk areas are no longer "is G1 loaded at all", but more
specific semantic alignment issues:

  - Whether GMR dof_pos order exactly matches IsaacGym control order.
  - Whether body_pos/body_rot/body_vel/body_ang_vel have the same meaning as
    IsaacGym rigid body states.
  - Whether AMP demo observations and policy/runtime observations are aligned.
  - Whether loco task_obs exposes the same command semantics as the reward.
